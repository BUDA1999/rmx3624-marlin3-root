# Desbloqueio (CVE-2022-38694)

## 1. Validar a vulnerabilidade no seu `uboot`

Build de julho/2025 pode já ter `uboot` corrigido. Cheque antes de escrever:

```bash
strings backups/$(date +%F)/uboot.img | grep -i -E 'secure|verify|spl-unlock' | head -30
```

Se o `uboot` não tiver o fluxo de verificação que o exploit espera, o `spl-unlock` não sobe e
o handshake trava — sinal de build corrigida. Nesse caso vá para `07-troubleshooting.md`.

## 2. Executar o unlock

```bash
cd CVE-2022-38694_unlock_bootloader
spd_dump --wait 300 \
  exec_addr 0x65015f08 \
  fdl fdl1-sign.bin 0x65000800 \
  fdl fdl2-sign.bin 0x9efffe00 \
  exec w uboot fdl2-cboot.bin reset
```

`fdl2-cboot.bin` é o `uboot` patchado do **ums9230** — pegue da pasta de config do repo, não de
outro SoC. O `exec_addr` é o ponto mais frágil: se travar em `Waiting`, está errado para o
`marlin3_lite`; teste os valores vizinhos da config.

## 3. Confirmar

```bash
fastboot devices
fastboot getvar unlocked        # deve retornar yes
```

No boot aparece a tela **orange state** ("device has been unlocked and can't be trusted").
O aparelho **faz factory reset** aqui. Reconfigure, reative depuração USB.

- [ ] `getvar unlocked` = `yes`
- [ ] `getvar flash.locked` = `no`
```

### `docs/04-root-magisk.md`

```markdown
# Root com Magisk

## 1. Desativar AVB

Com o bootloader destravado, o `vbmeta` ainda exige verificação e o boot patchado seria rejeitado.

```bash
fastboot --disable-verity --disable-verification flash vbmeta_a backups/<data>/vbmeta_a.img
fastboot --disable-verity --disable-verification flash vbmeta_b backups/<data>/vbmeta_b.img
```

## 2. Patchar o boot

Método on-device (mais confiável):

1. Instale o Magisk (canal stable) no aparelho
2. `adb push backups/<data>/boot_a.img /sdcard/`
3. Magisk → Instalar → **Selecionar e patchar um arquivo** → `boot_a.img`
4. `adb pull /sdcard/Download/magisk_patched-*.img ./boot_patched.img`

Verifique antes de flashar:

```bash
magiskboot unpack boot_patched.img && magiskboot cpio ramdisk.cpio test
```

## 3. Test-boot

```bash
fastboot boot boot_patched.img
```

Se subir e o Magisk mostrar root ativo, o patch está bom. Se der bootloop aqui, **nada foi
gravado** — só reiniciar e revisar.

## 4. Flash

```bash
fastboot flash boot_a boot_patched.img
fastboot flash boot_b boot_patched.img
fastboot reboot
```

## 5. Primeiro boot

Magisk pede reboot adicional para completar o setup. Depois: `adb shell su -c id` → `uid=0(root)`.

- [ ] AVB desativado nos 2 slots
- [ ] test-boot passou
- [ ] `su` responde
```

### `docs/06-restauracao-e-relock.md`

```markdown
# Restauração e relock

## Remover root (mantendo unlock)

```bash
fastboot flash boot_a backups/<data>/boot_a.img
fastboot flash boot_b backups/<data>/boot_b.img
```

## Voltar 100% stock (com lock)

Só com boot stock nos **dois** slots, senão o AVB falha e o aparelho não boota:

```bash
fastboot flash vbmeta_a backups/<data>/vbmeta_a.img
fastboot flash vbmeta_b backups/<data>/vbmeta_b.img
fastboot flashing lock
fastboot reboot
```

Verificação:

```bash
adb shell getprop ro.boot.flash.locked        # 1
adb shell getprop ro.boot.verifiedbootstate   # green
```

Se `flashing lock` responder `Not implement.`, o relock é feito zerando o marcador em
`miscdata` (offset 8192, 64 bytes) com o mesmo `spd_dump`. Marcador zerado = travado.

> Relock também faz factory reset. E não relocke com boot patchado — brick de verificação.
```

# Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| `Waiting` eterno no `spd_dump` | `exec_addr` errado p/ `marlin3_lite` | testar endereços vizinhos da config; conferir udev |
| Handshake cai após o FDL2 | `uboot` já corrigido | partir para EDL + PAC completo |
| `fastboot getvar unlocked` = `no` | exploit não gravou a flag | repetir; conferir se `fdl2-cboot.bin` é de ums9230 |
| Bootloop após flash | patch ruim ou AVB ativo | `fastboot flash boot_*` stock; refazer passo 1 do 04 |
| Sem boot nem fastboot | brick de bootloader | test point → BROM → flash do PAC inteiro |
| App de banco detecta root | DenyList incompleta | ver `05` |

## Test point

Só se BROM por botão falhar. Abra a traseira, ache o ponto marcado na placa (guia específico do
RMX3624), feche o ponto no GND com pinça e conecte o USB mantendo o contato. `lsusb` deve
mostrar o dispositivo. Depois é flash do PAC completo pelo ResearchDownload/`spd_dump`.
```

|---|---|---|---|
| `boot_a` / `boot_b` | kernel + ramdisk | obrigatório | alvo do Magisk |

| `nvdata`, `nvram`, `modem` | rádio | sim | não |
