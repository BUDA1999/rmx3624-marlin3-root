# RMX3624 (Realme C33) — Unisoc T612 / marlin3_lite — Unlock + Root

Projeto de desbloqueio de bootloader e root para o **RMX3624**, build **`RMX3624_13.C.46`**.

| Campo | Valor |
|---|---|
| Modelo | RMX3624 (Realme C33) |
| Build | `RMX3624_13.C.46` / `O_V1_P16` |
| Plataforma | `sc2355_marlin3_lite` (Unisoc UMS9230 / T612) |
| Kernel | `5.4.254-android12-9-g3bdf085cac44-ab1403` |
| Compilação | `#1 Tue Jul 8 16:49:47 CST 2025` |
| Android | 13 (realme UI 4.0) |
| Armazenamento | eMMC 5.1, A/B virtual (VAB) |
| Status | 🟡 Não iniciado — hipótese em validação |

## Estratégia

Desbloqueio por **CVE-2022-38694** (bypass de verificação de assinatura no `uboot` da Unisoc),
via `spd_dump` em modo BROM. Root por **Magisk** com `boot.img` patchado, AVB desativado no `vbmeta`.

KernelSU **não** é caminho aqui: `MODULE_SIG_FORCE=y` no `5.4.254` rejeita módulo não assinado
(`insmod` → `Key was rejected by service`). Só funcionaria com rebuild completo do kernel.

## Ordem de execução

1. `docs/01-pre-requisitos.md` — PAC do modelo, driver, host
2. `docs/02-backup-obrigatorio.md` — readback total antes de tocar em nada
3. `docs/03-desbloqueio-bootloader.md` — validação da CVE + unlock
4. `docs/04-root-magisk.md` — patch, test-boot, flash
5. `docs/05-verificacao-pos-root.md`
6. `docs/06-restauracao-e-relock.md` — sempre ensaiado antes

## Regras do projeto

- **Nunca** flashar sem checksum conferido e sem backup do slot alvo.
- **Sempre** `fastboot boot` (test-boot) antes de `fastboot flash`.
- Boot vai **nos dois slots** (`boot_a` e `boot_b`) — VAB alterna slot e um slot stock derruba o root.
- Todo passo destrutivo entra em `notes/LOG.md` com saída colada.
- Não relockar com root ativo: verde só volta com boot stock nos 2 slots.

# Perfil do dispositivo

## Identificação

- `ro.product.model` = RMX3624
- `ro.build.display.id` = RMX3624_13.C.46
- `ro.build.version.incremental` = O_V1_P16
- `ro.board.platform` = sc2355_marlin3_lite
- `uname -r` = 5.4.254-android12-9-g3bdf085cac44-ab1403
- `ro.build.date` = Tue Jul 8 16:49:47 CST 2025

## Por que estes dados importam

O sufixo `marlin3_lite` é a variante "lite" da plataforma marlin3 (UMS9230). Os endereços de
carregamento do FDL e o `exec_addr` **mudam entre variantes** — usar os de outro board
(T606/T616/T618) pode travar o handshake BROM. Sempre confirmar contra a config do SoC
correspondente no repo do exploit antes de rodar.

## Vetor de ataque

CVE-2022-38694: o verificador de assinatura do `uboot` da Unisoc aceita imagem não assinada.
Explorando, é possível executar código antes da verificação e gravar permanentemente a flag de
unlock nos registradores OTP do SoC. Resultado: estado "orange", `fastboot flashing unlock` liberado.

## Superfície de risco

| Item | Risco | Mitigação |
|---|---|---|
| Escrita no `uboot` | Alto — brick de bootloader | backup + `uboot_bak` intacto |
| Flag OTP | Irreversível em hardware | aceitar (não há undo real) |
| Wipe de dados | Certo | backup prévio |
| Slot B stock | Perda de root em troca de slot | flashar os 2 slots |
| Anti-rollback | Médio | não descer de versão após o unlock |
```

# Pré-requisitos

## Hardware / host

- PC com **Linux x86_64** (recomendado) ou Windows com `spd_dump.exe`
- Cabo USB de dados (não cabo de carga)
- Pinça ou fio para o **test point** (plano B)
- Bateria acima de 60%

## Software

```bash
sudo apt install -y libusb-1.0-0-dev build-essential android-tools-adb android-tools-fastboot
git clone https://github.com/TomKing062/CVE-2022-38694_unlock_bootloader
git clone https://github.com/ilyakurdyukov/spreadtrum_flash
cd spreadtrum_flash && make && sudo cp spd_dump /usr/local/bin/
```

Regra udev para acesso sem root (Linux):

```bash
echo 'SUBSYSTEM=="usb", ATTR{idVendor}=="1782", MODE="0666"' \
  | sudo tee /etc/udev/rules.d/99-sprd.rules
sudo udevadm control --reload-rules
```

`1782` é o VID da Spreadtrum/Unisoc. Confirme com `lsusb` quando o aparelho estiver em BROM.

## Firmware

Precisa do **PAC do RMX3624 na mesma família de build** (`13.C.*`). Do PAC saem os **FDL1/FDL2
assinados do próprio aparelho** — mais confiáveis que os genéricos que vêm no repo do exploit.
`boot.img` e `vbmeta.img` podem sair do próprio aparelho por readback, sem PAC.

## Checklist

- [ ] `adb devices` lista o aparelho
- [ ] `lsusb` mostra `1782:` em modo BROM
- [ ] PAC baixado e com SHA256 anotado
- [ ] `spd_dump --help` roda
- [ ] Depuração USB ativada e autorizada
- [ ] Conta realme/Google anotada (pós-wipe)
```
